# Ledgers-Postings Project Documentation for LLMs

## 1. Project Overview

This project is a Rust implementation of a ledger system based on double-entry bookkeeping principles, likely derived from or inspired by [adorsys/ledgers](https://github.com/adorsys/ledgers). It uses a layered architecture with a clear separation between data access, service logic (currently minimal), and a potential REST API layer (currently minimal).

The core functionality resides in the `postings-repository` crate, which handles database interactions for ledger entities.

## 2. Architecture & Workspace Structure

The project is organized as a Rust workspace containing three member crates:

*   **`postings-repository`**: The data persistence layer. It defines the database schema, data models (structs mapping to tables), and repository functions for CRUD operations and complex queries. Uses Diesel ORM with PostgreSQL.
*   **`postings-service`**: Intended to hold the core business logic, services, and use cases. Currently contains placeholder code.
*   **`postings-rest-server`**: Intended to provide an HTTP REST API interface to the ledger functionalities. Currently contains placeholder code.

The primary focus of the existing code is the `postings-repository`.

## 3. `postings-repository` Crate Deep Dive

### 3.1. Modules

*   **`src/models/`**: Contains the Rust structs that map to database tables (`mod.rs`) and custom database enums (`enums.rs`). These structs are primarily data holders (POPOs - Plain Old Plain Objects) with Serde support for serialization/deserialization and Diesel attributes for ORM mapping.
*   **`src/repository/mod.rs`**: Implements the **Repository Pattern**. It contains public modules (e.g., `posting_repository`, `ledger_account_repository`) where each module groups database query functions related to a specific model. **Crucially, query logic resides here, not in the model structs themselves.**
*   **`src/schema.rs`**: Auto-generated by Diesel CLI. Defines the database table structures and relationships as understood by Diesel. Also defines mappings for custom PostgreSQL ENUM types (`sql_types` submodule).
*   **`src/lib.rs`**: The crate root, simply declaring the public `models` and `repository` modules and the private `schema` module.
*   **`migrations/`**: Contains Diesel database migration files (`up.sql` for schema creation, `down.sql` for rollback). Defines the actual SQL `CREATE TABLE` and `CREATE TYPE` statements.
*   **`tests/`**: Contains integration tests for the repository functions. Uses helper functions from `common.rs` for database connection management and seeding.

### 3.2. Core Data Models (`src/models/mod.rs`)

Key entities representing the ledger system:

*   `ChartOfAccount`: Defines the overall structure of accounts.
*   `Ledger`: Represents a specific ledger (e.g., for a company). Linked to a `ChartOfAccount`.
*   `LedgerAccount`: Represents an individual account within a `Ledger`. Can have parent accounts, forming a hierarchy. Linked to `Ledger` and `ChartOfAccount`.
*   `Posting`: Represents a single, atomic financial operation or transaction recorded in the journal. Contains metadata like operation ID (`opr_id`), posting time (`pst_time`), recording time (`record_time`), status, type, etc. Linked to a `Ledger`.
*   `PostingLine`: Represents a single line item within a `Posting`, corresponding to a debit or credit entry against a specific `LedgerAccount`. A `Posting` typically has multiple `PostingLine` entries that must balance according to double-entry rules. Contains denormalized fields from `Posting` for efficiency.
*   `AccountStmt`, `LedgerStmt`: Represent snapshots or statements for accounts and ledgers, respectively.
*   `PostingTrace`: Links postings together, potentially for statement generation or tracking related operations.
*   `OperationDetails`: Stores potentially large details (e.g., JSON blobs) associated with an operation, referenced by `Posting` and `PostingLine`.
*   `OpNote`: For attaching notes or comments to records.

For each primary model (e.g., `Posting`), there's often a corresponding `New*` struct (e.g., `NewPosting`) used specifically for inserting new records via Diesel.

### 3.3. Custom Enums (`src/models/enums.rs`)

Defines Rust enums that map to PostgreSQL `ENUM` types using `diesel_derive_enum`:

*   `AccountCategory`: (RE, EX, AS, LI, EQ, etc.) - Classifies accounts.
*   `BalanceSide`: (Dr, Cr, DrCr) - Indicates the normal balance side of an account.
*   `PostingStatus`: (POSTED, DEFERRED, CANCELLED, etc.) - Tracks the lifecycle state of a posting.
*   `PostingType`: (BUSI_TX, ADJ_TX, BAL_STMT, etc.) - Categorizes the nature of the posting.
*   `StmtStatus`: (SIMULATED, CLOSED) - Status of ledger/account statements.

### 3.4. Repository Pattern (`src/repository/mod.rs`)

*   **Separation**: Database access logic is strictly separated from the models. Models are data containers; repositories perform operations.
*   **Organization**: Functions are grouped into modules named after the primary model they operate on (e.g., `posting_repository`, `ledger_account_repository`).
*   **Naming Convention**: Functions often mimic common query patterns (e.g., `find_by_id`, `find_by_opr_id`, `find_first_by_..._order_by_...`).
*   **Signatures**:
    *   Functions take a mutable reference to the `PgConnection`.
    *   Return types are typically `QueryResult<T>` where `T` might be `Vec<Model>`, `Option<Model>`, or `Model`. This propagates Diesel errors.
    *   `Option<Model>` is used when a query might reasonably find zero results (e.g., `find_by_id`).
    *   `Vec<Model>` is used when multiple results are expected.
*   **Implementation**: Uses Diesel's query builder DSL (`filter`, `order_by`, `limit`, `load`, `first`, `optional`, etc.).

### 3.5. Database Schema (`migrations/.../up.sql`, `src/schema.rs`)

*   Defines standard relational tables with primary keys (`id` usually `VARCHAR`) and foreign key constraints.
*   Uses PostgreSQL `ENUM` types for specific fields, mapped via `diesel-derive-enum` and `sql_types` in `schema.rs`.
*   Includes constraints like `UNIQUE`.
*   `schema.rs` reflects this structure for Diesel's use and defines `joinable!` relationships.

## 4. Testing (`postings-repository/tests/`)

*   **Integration Tests**: Tests interact with a real PostgreSQL database managed via Docker Compose.
*   **Test Setup (`common.rs`)**: Provides utility functions:
    *   `establish_connection()`: Connects to the test database configured via `.env` (`DATABASE_URL`). It includes logic to automatically start the required Docker Compose service (`postings-repository/compose-postgres.yml`) if it's not already running. **Note:** This function *does not* explicitly verify if the established connection points to the intended database/user defined in the environment; it relies on `PgConnection::establish` failing if the URL, credentials, or host are incorrect.
    *   `seed_database()`: Executes SQL scripts (from `tests/fixtures/`) to populate tables with test data before a test runs.
    *   `TestDatabaseGuard`: A struct implementing `Drop` to `TRUNCATE` relevant tables *after* a test runs, ensuring test isolation.
*   **Isolation**: The `#[serial]` attribute from the `serial_test` crate is used on test functions. This ensures that tests affecting the database run sequentially, not in parallel, preventing interference.
*   **Assertions**: Standard Rust `assert_eq!`, `assert!`, etc., are used to verify the results returned by repository functions against expected values based on the fixture data.
*   **Error Handling**: Tests often use `.unwrap()` or `.expect()` on `QueryResult` because test failures are expected if database operations fail. This is generally **not** done in application code. Double unwraps (`.unwrap().unwrap()`) are common when dealing with `QueryResult<Option<T>>`.
*   **Troubleshooting Conflicts**: A common issue is having another PostgreSQL instance running locally (or in another Docker container) that conflicts with the one intended for testing (usually by occupying the same port). If tests fail with connection or authentication errors:
    1.  Check for other running Postgres containers: `docker ps`
    2.  Stop the conflicting container: `docker stop <container_name_or_id>`
    3.  Optionally remove it: `docker rm <container_name_or_id>`
    4.  Rerun `cargo test`.

## 5. Development & Environment

*   **Database**: PostgreSQL, managed via Docker Compose (`compose-postgres.yml`) for development and testing. Includes Adminer for web-based DB inspection.
*   **Environment Variables**: `.env` file likely sets `DATABASE_URL`.
*   **Migrations**: `diesel migration run` applies schema changes.
*   **Dependencies**: Managed by `Cargo.toml`. Key dependencies include `diesel`, `chrono`, `serde`, `rust_decimal`, `diesel-derive-enum`, `serial_test`.

## 6. Key Conventions & LLM Guidance

*   **Repository Pattern is Key**: Understand that DB logic is in `repository/` modules, *not* methods on the model structs in `models/`. When asked to find how data is fetched, look in the corresponding repository module.
*   **Models are Data**: Structs in `models/` are primarily for holding data and ORM mapping. They don't contain behavior.
*   **Enums**: Custom DB enums are defined in `models/enums.rs` and mapped in `schema.rs` and `migrations`.
*   **Error Handling**: `QueryResult` is the standard return type for fallible DB operations in repositories.
*   **Testing**: Tests provide excellent examples of how repository functions are used. Look at `tests/` for usage patterns. Note the use of `#[serial]` and `TestDatabaseGuard` for DB test management.
